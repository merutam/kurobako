Protocol

Kurobako protocol, version 8: what a client needs to read, write and share items in plain and encrypted namespaces. Binary values in text are base64url without padding (RFC 4648 §5); every error is JSON, {"error": "…"}.

Using a client · Implementing a client

Using a client

What Kurobako does and how to drive it, with curl or k.mjs.

Model

A namespace is a short queue of items (texts and files), newest first. A plain one, /<name>, is stored as sent. An encrypted one, /e#<secret name>, is sealed by the client; the server only sees /e/<id>. A namespace exists once something is sent to it and keeps its maxItems newest items, each until it expires.

The address is the write capability. Knowing a plain name lets anyone read and write it. An encrypted namespace is read with keys derived from its secret name, and every write, the first included, carries the Write-Key derived from it: missing, 401; wrong, 403. There are no accounts and no owners.

Requests

Every request works with curl. Below, $BOX is the site (BOX=https://<site>) and ns a plain namespace; an encrypted one answers the same paths at /e/<id> (see below). 1 stands for an item: its position (1 is the newest), its six-letter ID, or, in a plain namespace, its name or the start of it, ignoring case ($BOX/ns/report finds Report 2024.pdf).

Reading

Command Answer
curl $BOX/ns/ls the queue as JSON, newest first; X-Queue-Revision names the snapshot
curl "$BOX/ns/ls?summary" the same, long texts cut to a preview
curl "$BOX/ns/ls?limit=1" only the n newest (with summary too); the revision is still the whole queue's
curl $BOX/ns/1 its contents (/c is the same)
curl -OJ $BOX/ns/1/d saved under its own name
curl -r 0-1023 $BOX/ns/1 part of a file: 206 with those bytes (one range)
curl $BOX/ns/1.json the item, its position and shareUrl
curl $BOX/ns/1/s its share link, as text; one per item, always the same
curl $BOX/ns/log.json the addresses that opened the namespace
websocat wss://<site>/ns/live a WebSocket of changes (see Live updates)

Writing

Command Does
curl -d 'hello' $BOX/ns/new sends a text: 201 with the item
curl --data-binary @notes.md $BOX/ns/new a text from a file, line breaks kept (-d @file drops them, as curl does)
curl -H 'X-Text-Name: notes.md' -d '# hi' $BOX/ns/new a text with its name (percent-encoded); without one, it goes by its first words
curl -T photo.jpg $BOX/ns/ sends a file, named after it (PUT /ns/<filename>)
curl -H 'Burn: 1' -d 'once' $BOX/ns/new deleted when first read
curl -H 'Reads: 3' -H 'Expires-In: 3600' -d 'hi' $BOX/ns/new three reads, gone after an hour
curl -H 'If-Match: "<updatedAt>"' -d 'changed' $BOX/ns/1/e replaces a text's contents if unchanged since that version (else 412); before any change, use createdAt
curl -X POST -T notes.tar -H 'If-Match: "<updatedAt>"' $BOX/ns/1/e replaces a bundle with another (sent as a file, so -T, not -d); X-Filename renames it
curl -d 'new name' $BOX/ns/1/n renames it; an empty name gives a text back its default
curl -X DELETE $BOX/ns/1 {"ok": true}

Backups

Command Does
curl -OJ $BOX/ns/zip the namespace as ns-<date>.zip (/tar for a tar)
curl -OJ "$BOX/ns/zip?since=2026-10-01" only items sent or changed since; deletions are not recorded
curl -D - -OJ "$BOX/ns/zip?max=100000000" in parts of about that size; while more remain, X-Kurobako-Next goes back as ?after=
curl -T ns-2026-10-06.zip $BOX/ns/import puts it back: {"restored", "skipped", "rejected"}

Bundles

A bundle sends texts and files together as one item, so that a Markdown text shows with its images: a tar whose first entry is kurobako.json, the manifest (see its format).

Command Does
tar -cf notes.tar kurobako.json notes.md assets/photo.png makes one, the manifest first
curl -T notes.tar $BOX/ns/ sends it
curl -OJ $BOX/ns/1/d && tar -xf notes.tar gets it back

Sharing

/i/<token> opens one item without revealing its namespace, until the item is gone ($BOX/ns/1/s gives it). An encrypted item's link carries its key after the #, which never reaches the server and opens that item alone.

/v/<token>, a view, lists item links without revealing the namespace. One view per namespace is active and gains new sends; making another freezes which items the old one lists, while their contents stay live. A namespace keeps at most 100 views.

curl $BOX/v/<token>/ls lists its items as JSON, with each share token as the item ID. /i/<token>/ls lists the one shared item. Both accept ?summary and ?limit=1 like a namespace's /ls. For encrypted links, node k.mjs "$BOX/v/<token>#<view-key>/ls" prints the decrypted items as a JSON array.

Command line: k.mjs

k.mjs implements this protocol as a command line with curl's options (Node 20+ or Bun, no dependencies; curl -O $BOX/k.mjs). Every command on this page works as node k.mjs, on a plain namespace as it is and on an encrypted one with "$BOX/e#<secret name>" in place of $BOX/ns: it seals what it sends, opens what comes back, and adds the Write-Key and, for edits, the If-Match. Share links come with the item's key after the #. It does more than curl, such as exporting a namespace, following it live and reading a backup offline: node k.mjs --help shows it all.

Implementing a client

What a client needs beyond the commands above: the server's description, the formats, live updates and the encryption, with test vectors.

Discovery

GET /.well-known/kurobako describes the server. Every path below goes after its base ("" or e.g. "/k").

protocol the version of everything this page describes, 8: its requests, formats and encryption. A client written for another version may not work with this server
maxFileBytes, maxTextBytes size limits; texts past inlineTextBytes are listed with a preview
maxItems, itemTtlSeconds queue length and default lifetime (0: no expiry)
sendsPerMinute, missesPerMinute sends, and requests for what is not there, a client may make in a minute; past them, 429 with Retry-After
maxStorageBytes all items together, or null; a send that does not fit gets 507
namespace, sealed plain names' pattern, maxLength and reserved names; sealed.maxNameLength
live the WebSocket's ping/pong messages and pingSeconds
private if true, requests need Authorization: Bearer <key> or get 401 (share links may be exempt)

Items

Every item has id, kind, size (bytes), createdAt, updatedAt once changed, and expiresAt (null: never). In a plain namespace, kind is text (with name, and text or preview), image or file (with filename and mime). Types come from the bytes: PNG, JPEG, GIF, WebP, AVIF and HEIC are images, and so is SVG (text whose root element is <svg, within its first 1,024 bytes, after at most a declaration, comments and a doctype without [); MP4, MOV, WebM and Matroska are files with a video/* type; anything else is application/octet-stream. Contents are served with Content-Security-Policy: default-src 'none'; sandbox, so an SVG's scripts never run.

Sending, in detail

  • Content-Type: text/plain or application/x-www-form-urlencoded sends a UTF-8 text, named by percent-encoded X-Text-Name or else by its first words (up to 80 characters). Any other type sends a file, named by percent-encoded X-Filename.
  • Nothing is empty: a send or edit without contents gets 400.
  • Expires-In: <seconds> shortens the lifetime (at most 30 days when the server has none). Reads: <n> (1–1,000,000) deletes the item after n reads of its contents; Burn: 1 means one, shown as burn: true, more as readsLeft. Listing, .json and /s are not reads. Such items have no preview, no name, no ranges and no place in backups.
  • Sending contents already in a plain queue moves that item to the top (200, "existing": true) unless the send has No-Dedup: 1.
  • Edits and encrypted renames send If-Match: "<updatedAt or createdAt>": without it, 400; if the item changed since, 412. A text becomes another text and a bundle another bundle; other files and read-limited items cannot be edited.

Backup archives

An archive holds manifest.json first, then each item's contents at its path; encrypted items stay sealed, as <id>.sealed with their metadata in the manifest: 

{"kurobako": "backup", "version": 1, "exportedAt": "2026-10-11T18:03:51.578Z",
 "namespaces": [{"space": "plain", "name": "ns", "items": [
   {"id": "erqgrq", "kind": "text", "createdAt": "…", "expiresAt": "…",
    "size": 4, "path": "plain/ns/notes.md", "name": "notes.md"},
   {"id": "bslclk", "kind": "image", "createdAt": "…", "expiresAt": "…",
    "size": 28, "path": "plain/ns/photo.png", "filename": "photo.png", "mime": "image/png"}]}]}

An encrypted namespace is "space": "sealed", its ID as the name, and items at sealed/<ID>/<id>.sealed. updatedAt appears once an item changed; a part of a backup in parts carries "next". An import keeps IDs and dates, skips what is there, applies newer text contents and names, and never deletes; an encrypted namespace only takes its own items. Read-limited items are left out.

Live updates

<ns>/live sends {"type": "ready", "revision": n}, then {"type": "change", "revision", "upserts", "removed", "order"} for each change and {"type": "viewers", "count"} when pages open or close. Connect first, then fetch ls?summary and apply the buffered changes newer than its X-Queue-Revision; on a gap in revisions, fetch again. After a drop, start over the same way: connect, then fetch. Send live.ping as a text message every pingSeconds; the answer is live.pong, and two intervals without a word from the server mean the connection is gone.

Bundle format

Any file whose first bytes are kurobako.json and a NUL is a bundle: typed application/vnd.kurobako.bundle+tar and named .tar (by the server for plain sends, by the client for encrypted ones). It is otherwise a file like any other: one item, within maxFileBytes, downloaded as the tar it is.

The manifest lists the entries in the order a client shows them, and which text comes first: {"kurobako": "bundle", "version": 1, "main": "notes.md", "entries": [{"path": "notes.md", "type": "text/markdown", "text": true}, {"path": "assets/photo.png", "type": "image/png"}]}. Texts sit at the root and files under assets/; paths are unique and at most 100 bytes of UTF-8. Entries with "text": true are texts, shown as tabs (Markdown, by a .md name, rendered); the others are files. A text refers to a file by its path, as ![](assets/photo.png) or [notes](assets/report.pdf), which also reads right once the tar is extracted. Clients show only what the bundle holds: no HTML, and no images from elsewhere.

Encrypted namespaces

The secret name derives the namespace ID (the address), the write key and the namespace key. Each item has a random item key, which seals its metadata and contents and is wrapped with the namespace key. Ciphers: AES-128-GCM, and AES-KW for wrapping. Every key is 16 bytes but K.

For From Label (salt, HKDF info or AES-GCM data)
K, 32 bytes the name, PBKDF2 kurobako/v4
write key K, HKDF kurobako/v4/write
namespace key K, HKDF kurobako/v4/namespace
sealed metadata item key, AES-GCM kurobako/v4/metadata
body key item key, HKDF kurobako/v4/body/0, or kurobako/v4/body/<rev>/<bodyId> once replaced
view key K, HKDF kurobako/v6/view/<viewId>
view entry (an item key) view key, AES-GCM kurobako/v6/view-entry/<viewId>

A label names the protocol version that brought it in, and never changes: another label makes other keys, and every existing namespace unreadable.

Keys

  1. Normalize the name: Unicode NFC, then trimmed of the whitespace JavaScript's String.prototype.trim() removes: U+0009–U+000D, U+0020, U+00A0, U+1680, U+2000–U+200A, U+2028, U+2029, U+202F, U+205F, U+3000 and U+FEFF, but not U+0085, which other languages trim. Another set of whitespace derives other keys from the same name. The name cannot contain /, which starts a path in a link (/e#name/ls), and has at most sealed.maxNameLength UTF-16 code units, as JavaScript counts a string (an emoji outside the BMP counts two).
  2. K = PBKDF2-SHA-256(the name in UTF-8, salt kurobako/v4, 600,000 iterations), 32 bytes.
  3. From K, HKDF-SHA-256 with an empty salt, 16 bytes each: the write key (info kurobako/v4/write), sent as Write-Key: base64url(write key); the namespace key (info kurobako/v4/namespace), which only wraps item keys (RFC 3394).
  4. The namespace ID is the first 16 bytes of SHA-256(base64url(write key)), in base64url. The server checks a Write-Key by hashing it the same way, so it needs nothing stored to accept the first write.
  5. A read-only link, /e#/<token>, carries base64url(namespace ID ‖ namespace key): it reads everything and cannot write.

The name is the only secret: anyone with a copy of the server's data can try names offline at about 15,000 a second per GPU. A random name of 16 characters (about 80 bits) holds for ages; a phrase someone would pick falls in seconds.

A wrong name is no error: it derives another namespace, most likely empty. An item that does not open is damaged or sealed with another key; AES-GCM cannot tell which.

Sealing

Seal(key, label, data) is a random 12-byte IV, then the AES-GCM ciphertext and its 16-byte tag, with the label in UTF-8 as additional data. Metadata is sealed with the item key under kurobako/v4/metadata.

Contents are sealed in segments, so that any part opens alone:

  • The body key is HKDF-SHA-256(item key, empty salt, info kurobako/v4/body/0), 16 bytes; for a replacement, info kurobako/v4/body/<rev>/<bodyId>.
  • Contents are cut into 65,536-byte pieces, the last shorter and never empty. Piece i is sealed with the body key, no additional data, and the nonce i in 11 big-endian bytes followed by 1 for the last piece, 0 otherwise.
  • The body is the segments end to end: n bytes of contents make n + 16⌈n / 65,536⌉. Segment i starts at i × 65,552, so a Range fetches any part.

Items

Metadata is JSON: {"title": "…"} for a text ({} for a read-limited one), {"filename": "…", "mime": "…"} for a file, typed by the same rules as plain files (mime left out for application/octet-stream). A replacement adds "rev": n and "bodyId", 16 random bytes for each attempt, so concurrent edits never reuse a key; a nonzero rev without a valid bodyId is rejected.

A send is the sealed body with X-Sealed-Metadata: base64url(AES-KW(namespace key, item key)) "." base64url(Seal(item key, metadata)) and Write-Key. The queue lists it as kind: "sealed" with that metadata. Edits and renames send a new X-Sealed-Metadata with the same wrapped key. <item> is a position or an ID: the server cannot read names.

curl still reaches an encrypted namespace, but only sees what the server sees: curl $BOX/e/<id>/ls lists sealed items, curl -OJ $BOX/e/<id>/zip backs it up without the name, and writes need -H "Write-Key: …" and a body sealed as above. To work with the contents, use a client that does the sealing, such as k.mjs.

Sharing

An item link's .json gives the item (without its ID), /c its contents and /d a download. For an encrypted item, the link is /i/<token>#<base64url(item key)>: open the second part of its metadata and its contents with that key.

  • GET <ns>/views gives the current items, past views and the active token. POST <ns>/views makes a view: {"viewId", "previousToken", "entries": [{"id"}]}, with viewId 16 random bytes and the entries matching the queue exactly; otherwise 409.
  • GET /v/<token>.json gives the viewId, whether it is active, and each entry's /i/ URL and item.
  • GET /v/<token>/ls gives an array of items with their public share tokens as IDs. Encrypted entries also carry their viewId and envelope. GET /i/<token>/ls gives a one-item array.
  • Encrypted: the link is /v/<token>#<base64url(view key)>, the view key being HKDF-SHA-256(K, empty salt, info kurobako/v6/view/<viewId>), 16 bytes. Each entry carries an envelope: the item key sealed with the view key under kurobako/v6/view-entry/<viewId>. Sends to a namespace with an active view add View-Token and View-Envelope, or get 409.
