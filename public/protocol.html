Protocol

This page is the complete protocol of a Kurobako server, for plain and encrypted namespaces. With what is below, and nothing else, a client can read, write, rename, delete, download and share items. k.mjs is one such client; nothing in it is needed to interoperate.

Overview

A namespace is a short queue of items (texts and files), newest first, that every device opening it shares. A plain namespace, /<name>, is stored as sent and works with curl alone. An encrypted one, /e#<secret name>, is encrypted in the client: the secret name never reaches the server, which only sees /e/<id>. Both answer the same requests; what differs is what goes in and comes out. Binary values in text form are base64url without padding (RFC 4648 §5).

Server and limits

GET /.well-known/kurobako describes the server as JSON: base, the path the site lives under ("" at the domain's root, or e.g. "/k"; every path on this page goes after it), version, protocolUrl (this page), clientUrl (k.mjs), and its limits: maxFileBytes, maxTextBytes, inlineTextBytes (longer texts are listed with a preview), maxItems (older items fall off the queue), itemTtlSeconds (0: no expiry), sendsPerMinute per client address (an IPv6 address counts by its /64 network), maxStorageBytes (every item together; null: no limit), namespace (the pattern, maxLength and reserved names of plain namespaces), sealed.maxNameLength and live (the WebSocket's ping and pong messages, pingSeconds between pings, and hiddenCloseSeconds, how long a hidden page keeps its connection). A send beyond the limit gets 429, so wait for the minute to pass; one that would fill the storage gets 507. A client that asks for more than missesPerMinute namespaces, items or share links that are not there in a minute (a 404, or an empty queue) gets 429 for every read of a namespace or share link until the minute is over. Depending on automatedNetworks, sends from hosting, cloud and VPN networks or Tor are counted by network block ("limit") or refused with 403 ("block"). Every error is JSON: {"error": "…"}. With "private": true, every request but this one and the protocol needs Authorization: Bearer <key>, or gets 401; share links open without it unless the instance keeps them private too.

Every namespace

Below, <ns> is /<name> or /e/<id>. A namespace exists once something is sent to it; it keeps the maxItems newest items, each for itemTtlSeconds. <item> is an item's position (1 is the newest) or its six-letter ID, which never changes; plain namespaces also take its name (below).

Request Answer
GET <ns>/ls the queue as JSON, newest first; ?summary cuts long texts to a preview
GET <ns>/<item> its contents (/c too, as on a share link); /d as a download, under its name (an encrypted item's is sealed, so it is <id>.sealed). A file takes one Range: bytes=… and answers 206 with that part, as players ask to start and seek; a burn-after-reading item is always read whole
GET <ns>/<item>.json the item, its position and a shareUrl
GET <ns>/<item>/s the share link alone, as text (POST works too); one per item, always the same
DELETE <ns>/<item> {"ok": true}
GET <ns>/log who opened the namespace, as a page; log.json as JSON
GET <ns>/live a WebSocket: the queue (as ?summary) on connecting and after every change, as {"type": "items", "items": […]}; how many pages are open on the namespace (the receiver's included) whenever one opens or closes, as {"type": "viewers", "count": …}; send live.ping (ping) and get live.pong (pong)
GET <ns>/zip, /tar the namespace as an archive: manifest.json first (each item's details and the path of its contents), then the contents; encrypted items stay sealed (<id>.sealed, their header in the manifest). ?since=<date>: only items sent or renamed since; deletions are not recorded. Burn-after-reading items are left out. ?max=<bytes>: in parts, each a whole backup of its own items, stopping at about that size; while more remain, the X-Kurobako-Next header (also next in the manifest), given back as ?after=, is the next part.
POST <ns>/import puts such an archive back (PUT too), keeping IDs and dates, applying newer names and skipping what is already there: {"restored": …, "skipped": …, "rejected": …}. An import never deletes or replaces existing contents. Restore into an empty instance for an exact copy. An encrypted namespace only takes back its own items.

Each item has id, kind, size (bytes), createdAt, optional updatedAt after a metadata change, and expiresAt (null without expiry). Its contents are at <ns>/<id>/c and a download at <ns>/<id>/d, as on a share link; the JSON carries no links. burn: true marks one deleted by its first read. Sending with the header Burn: 1 makes one; reading its contents consumes it, while ls, .json and /s read nothing.

Plain namespaces

A name is 1-64 characters of a-z, 0-9, - and _, starting and ending with a letter or digit; a, e, i and k are taken.

Request Does
POST /<name>/new sends an item. Content-Type: text/plain or application/x-www-form-urlencoded (what curl -d sends) makes a UTF-8 text; any other type, a file, named by X-Filename (percent-encoded). 201 with the item.
PUT /<name>/<filename> sends a file under that name (curl -T file /<name>/)
POST /<name>/<item>/n renames it: the body is the new name; an empty one gives a text back its default
  • Items: kind is text, image or file. A text has name and text, or, beyond inlineTextBytes, a preview of its first 280 characters; a file or image has filename and mime.
  • Types come from the bytes: PNG, JPEG, GIF, WebP, AVIF and HEIC are images (kind: "image"), served inline. MP4, MOV, WebM and Matroska are videos: still kind: "file", with their mime (video/mp4, video/quicktime, video/webm, video/x-matroska), so a page can play them. Images and videos are named with their own extension. Anything else is served as application/octet-stream.
  • Names: a text is named by its first words until renamed (burn-after-reading texts have none). An <item> may also be a name, exact or the start of one, ignoring case; the newest match wins (/notes/report finds Report 2024.pdf).
  • No copies: sending contents already in the queue moves that item to the top instead, renamed if the send gives a name: 200 with "existing": true.

Encrypted namespaces

The secret name stays on the device, where it derives a namespace ID, which the server uses to find the namespace, and a namespace key. Each item has its own random item key, which encrypts its contents and metadata and is wrapped with the namespace key. A share link carries one item key and opens that one item. Items are encrypted with AES-128-GCM; item keys are wrapped with AES-KW.

Namespace ID and key

  1. Normalize the name: Unicode NFC, then trim surrounding whitespace. The name cannot contain /, which in a link (/e#name/ls) starts the path.
  2. Derive K, 32 bytes (one SHA-256 block), with PBKDF2:
    Hash SHA-256
    Password the normalized name, UTF-8
    Salt kurobako/v4 (UTF-8)
    Iterations 600,000
    Output 256 bits (32 bytes)
  3. From K, with HKDF-SHA256 (an empty salt; the info is the label, in UTF-8), 16 bytes each: namespace ID, info kurobako/v4/id, in base64url (22 characters): the namespace lives at /e/<id>/…; write key, info kurobako/v4/write, in base64url: the Write-Key of a locked namespace (see Locked namespaces), so its owner never handles a key; namespace key, info kurobako/v4/namespace, an AES-128 key that only wraps item keys, with AES-KW (RFC 3394).
  4. A read-only link, /e#/<token>, carries base64url(namespace ID ‖ namespace key), 43 characters, and never K: it reads everything, and cannot give the write key. The empty name before its / is no name at all.

How strong a name is

An encrypted namespace is as safe as its name is hard to guess. The server stores each namespace under its ID, so anyone holding a copy of its data (whoever runs it, a leak, the hosting provider) can try names offline: derive the ID of each guess and look for it. The 600,000 PBKDF2 iterations make each guess slow, roughly 15,000 a second on a fast GPU; without that data, every guess has to go through the site itself. With 1,000 such GPUs:

Name About To guess
Random name (16 characters) 80 bits a billion years
4 random words from a large dictionary 50 bits 2 years
3 random words 38 bits 4 hours
a personal phrase (joao2024, beach house) 20-30 bits seconds

The home page counts a typed name at 2.5 bits a character at most, since names people pick follow patterns: words, dates, names.

Sealing

Seal(key, label, plaintext) = a random 12-byte IV, then the AES-GCM ciphertext with its 16-byte authentication tag at the end (exactly what Web Crypto's encrypt returns), with the label, in UTF-8, as additional authenticated data: it is checked, never sent. Metadata is sealed so, under the label kurobako/v4/metadata. Open reverses it, with the same label, and fails if anything was changed.

Contents are sealed in segments, so that a part of them opens without the rest (to play a video from its middle, or to download a large file as it arrives):

  • Body key: HKDF-SHA256(item key, an empty salt, info kurobako/v4/body/<rev>), 16 bytes, where rev is the contents' revision (0 when sent; see the metadata). Each new revision has its own key, so no nonce is ever used twice under one key, while the item key, and every share link that carries it, stays the same.
  • The contents are cut into pieces of 65,536 bytes, the last one shorter and never empty. Piece i becomes its AES-GCM ciphertext and 16-byte tag under the body key, with no additional data and a 12-byte nonce: i in 11 big-endian bytes, then 1 for the last piece and 0 for the others. A segment cannot be moved, dropped from the end, or taken from another body.
  • The body is the segments, one after the other: no header, no IV. With n bytes of contents in k = ⌈n / 65,536⌉ segments, it is n + 16k bytes; from a body of c bytes, k = ⌈c / 65,552⌉ and n = c − 16k.
  • Bytes a to b of the contents are in segments a ÷ 65,536 to b ÷ 65,536; segment i starts at i × 65,552 in the body. A client asks for those with Range, opens them and cuts the ends.

Items

  1. Pick a random 16-byte item key (AES-128-GCM).
  2. Metadata is JSON, sealed with the item key, holding only what cannot be told otherwise:
    A text {"title": "…"}, a short title; {} without one (burn-after-reading texts)
    A file {"filename": "…", "mime": "…"}, by the server's rules for plain files: an image told by its first bytes (as listed under Plain namespaces) gets its type and its own extension; anything else is application/octet-stream, which is left out
    Either adds "rev": n once its contents were replaced (0, left out, until then). An item with a filename is a file; any other, a text. Its size is told by the body's, as the queue lists it (see the segments above).
  3. The X-Sealed-Metadata header is base64url(AES-KW(namespace key, item key)) "." base64url(Seal(item key, kurobako/v4/metadata, metadata JSON)); the wrapped key is 24 bytes.
  4. The body is the contents sealed in segments, under the body key of rev 0; a text's contents are its UTF-8 bytes.

Requests

The requests for every namespace, at /e/<id>, plus these. Each item in the queue has kind: "sealed" and metadata, the X-Sealed-Metadata it was sent with; its contents are the sealed body. <item> is a position or an ID only: the server cannot read names, so a client looks them up in the decrypted queue. A shareUrl or /s link needs # and the item key added.

Request Does
POST /e/<id>/new sends an item: the sealed body, with X-Sealed-Metadata and Content-Length; 201 with the item
POST /e/<id>/<item>/n renames it: X-Sealed-Metadata with the same wrapped key and the metadata sealed again with the item key

Locked namespaces

A locked namespace is read by anyone who reaches it and written only with its write key, sent as the Write-Key header. The server keeps only the key's SHA-256. Every write needs it: new, PUT, /n, DELETE, import and /s (a share link is made, and kept, on the server); .json leaves out shareUrl for a reader. Without the key a write gets 401, with a wrong one 403, which counts as a miss. A locked namespace takes no burn-after-reading items (400): its readers are many, and the first would delete one for all. ls answers with the header Locked: 1, and the live queue carries "locked": true.

Request Does
POST <ns>/lock locks it. A plain namespace locks only while empty, so nobody takes one others use, and gets {"locked": true, "writeKey": "…"}: a key the server makes (22 characters), given once, unless Write-Key brings one. An encrypted namespace brings the key its client derives. Already locked, the same request with the current key gives a plain namespace a new one. 409 for a plain namespace with items
DELETE <ns>/lock with the key, opens it to every writer again: {"locked": false}

A lock lasts as long as its namespace: one locked and left empty is cleaned up like any other. The page keeps a plain namespace's key on the device; /<name>#w=<key> brings it to another one, in the fragment the server never sees.

Share links

/i/<token> opens one item without revealing its namespace, and stops working when the item is gone. GET /i/<token> is a page; .json gives the item (without its ID), /c its contents and /d a download.

A shared encrypted item is /i/<token>#<base64url(item key)>. The part after # never reaches the server. GET /i/<token>.json returns the item, whose metadata field is the X-Sealed-Metadata value it was sent with. Its second part, after the ., is the metadata sealed with the item key: open it with the key from the link. The first part, the item key sealed with the namespace key, is not needed. GET /i/<token>/c returns the sealed contents, which open with the same key.

Command line

k.mjs is the code this site runs and a command-line client that speaks curl (Node 20 or newer, or Bun; no dependencies): the same options and paths as the plain API, with <link> being https://<site>/e#<secret name> in place of the namespace. It encrypts what it sends and decrypts what comes back. Get it with curl -O https://<site>/k.mjs; https:// may be left out of links.

Command Does
node k.mjs <link>/ls the queue as JSON, decrypted
node k.mjs <link>/1 an item's contents: by position (1 is the newest), ID or name
node k.mjs <link>/1.json its details, position and share link (with the item's key), decrypted
node k.mjs -OJ <link>/1/d that item, saved under its own name (-o <file> picks the file)
node k.mjs -d "text" <link>/new sends a text; -d @file and -d @- (standard input) too, without line breaks as in curl; --data-binary @file keeps them
node k.mjs -T photo.jpg <link>/ sends a file
node k.mjs -H burn:1 -d "text" <link>/new sends an item deleted by its first read
node k.mjs -d "new name" <link>/1/n renames an item; an empty name gives a text back its default
node k.mjs -X DELETE <link>/1 deletes an item
node k.mjs <link>/1/s a share link, with the item's key after the #
node k.mjs <link> the items, one per line, reading none
node k.mjs -O <link> exports every item here, under its name (a text's with .txt)
node k.mjs https://<site>/i/<token>#<key> a shared item's contents

As with curl, binary contents are never written to a terminal and -O overwrites its output; --no-clobber refuses instead. Exporting a namespace does not delete extra local files. Reading a burn-after-reading item deletes it; listing reads nothing. Plain links work too, sent as they are. JSON prints the same for both, and an error is a message on standard error with exit status 1. A backup extracted to a folder reads like a namespace: <path>/ls, <path>/1, <path>/<id> and <path>/1.json for a plain one, and <path>/plain/<name>/ls and so on for one namespace of a whole instance's backup. An encrypted backup, or one of its .sealed files, takes <path>#<secret name> and the same paths. Its manifest.json must be there.
